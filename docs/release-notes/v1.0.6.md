## Mackit 1.0.6

Launch at login, fixed for real — and the menu bar icon stops disappearing.

- **The menu bar icon no longer vanishes after an update.** A login item registration caches a launch constraint computed from the agent binary at registration time — a code-directory hash for an ad-hoc-signed build, an identifier + team pair for a Developer-ID-signed one. Replacing that binary (a rebuild, an update, a reinstall) left the constraint pointing at a hash that no longer exists, so the kernel killed the agent at every login with a "Launch Constraint Violation" and launchd removed the service on the spot: the icon never appeared, the entry it left behind stopped resolving, and a spawn retry failed every ten seconds, forever. The app now rebuilds the registration at every launch when it is missing or was built from a different agent binary — tracked by the binary's code-directory hash, since a rebuild of the same commit changes the hash while leaving the version untouched — so a replaced binary repairs itself the next time you open the app instead of waiting for the next login to fail. A registration still awaiting your approval in System Settings is left alone rather than churned on every launch.
- **Your choice survives the system giving up on it.** The launch-at-login choice was read from the system state, so a registration the system had removed silently flipped the settings toggle off — losing your choice exactly when it needed rebuilding. The choice is now persisted in settings, with the system registration as the fallback only for settings files written before the choice was stored, and turning the toggle back on goes through the same rebuild, so it actually repairs a registration the system had abandoned.
- **Turning launch at login off no longer kills the tray.** Unregistering a login item makes launchd kill the process it spawned for it — the very menu bar icon you were looking at — even though the setting only ever decided whether the agent starts at login. The agent is now brought back through LaunchServices after unregistering, whose instances the login item has no hold on, so the tray survives the toggle and only the login-time start is affected.
- **One empty state, one set of metrics.** The welcome page, the general module's empty state and the disk analysis page's placeholders were six hand-written variants of the same prompt that had drifted into six sets of metrics. They now share a single composition, so the front door reads the same whichever module you open, while the compact in-column placeholders keep their smaller scale and skip the entrance animation, which would replay on every navigation and read as lag.

### Under the hood

- **The persisted-choice rule has one home.** `LaunchAtLogin.preferredIntent` encodes "read the persisted key, fall back to the system registration", and both the settings load and the launch-time repair read the choice through it, so the two paths cannot drift apart.
- **The repair decision is a pure function of observable state.** Given the registration status and the binary's code-directory hash, `needsRepair` answers whether a rebuild is needed; every branch — healthy, replaced binary, no record, missing registration, approval pending — is pinned by a unit test, together with the persisted-choice read and the settings round-trip. 361 tests across 41 suites pass.
