## Mackit 1.0.5

A new tool for the question every Mac user eventually asks: where did the space go? Disk space analysis measures the whole startup disk in one pass and presents the result as a treemap you can drill into, from the volume down to the container holding the junk.

- **A tool page of its own**: the sidebar has a new "Tools" section with a "Disk Analysis" row, sitting below the cleanup entries — a different kind of destination from either cleanup module. The hardware page's "Analyze Disk Space" now opens it too, instead of running a cleanup scan and dropping you back on the item list with no overview.
- **It waits for you to ask**: a whole-disk traversal is minutes of IO, so the page opens on a start screen and scans when you press the button — never on arrival. Once it runs, the scanning screen shows the folder being measured right now, the exact elapsed time and a "Stop Scan" button, and the results appear only after the scan has landed, so no number on screen is still moving while you read it.
- **"About 2 minutes left" is a real answer, not a guess**: the ring fills to an actual percentage, with a remaining time extrapolated from the rate measured so far. A filesystem walk's total is unknowable up front, so the first scan of a tree counts it concurrently — a names-and-types-only walk that never reads a file's inode, running on a few workers beside the measurement — and that count is remembered per tree, so every later scan divides by it directly instead of counting again. Approving a protected folder mid-session changes the skip set, so the stale count is dropped rather than stranding the ring at 100%; trees too small to reach the sample floor simply show the elapsed time.
- **Where the space went, at a glance**: the left column lists the current directory's children with their recursive sizes and item counts, biggest first. The right column shows the selected folder's breakdown as a squarified treemap — area proportional to size, largest first — with a "Visualization Mode" toggle for a plain list. Navigation is a breadcrumb with back and forward history, and a toolbar shortcut jumps straight to your home folder: the fastest path to `~/Library/Containers`, where most reclaimable container junk lives.
- **Readable at any size**: a folder with hundreds of children no longer turns into a field of unlabelled fragments. Every child big enough to carry a name keeps its own tile with its true area; the rest — everything under about 57×57pt — folds into a single "18 other items" block occupying exactly the area those children add up to, which opens a list of all of them, still enterable and still revealable in Finder. A name is now measured against the space its tile actually has, so it is drawn whole, truncated once, or not at all instead of wrapping mid-word; a large tile carries its percentage of the folder beside its size; and hovering a tile too small to read floats its name, size and share beside it.
- **Six levels, and one click more**: the scan retains six levels of the tree — the boundary that keeps the tool's footprint in the tens of megabytes on a real ~500 GB volume, where eight levels would hold over a million nodes. Drilling past it scans that folder the same way the whole disk was scanned — scanning screen first, results after — so `Users › … › Library › Containers › <container> › Data` stays reachable at any depth.
- **Honest about what it could not measure**: a folder the process may not read is reported as "This folder can't be read" rather than claiming "0 B", and `~/Documents`, `~/Desktop` and `~/Downloads` are listed as "Not scanned" instead of being silently skipped. Scanning one is an explicit action, so no access dialog interrupts a scan — and a link to the Full Disk Access pane is offered for a complete scan. Mount points and symlinks are left out entirely: their bytes are either another volume's or already counted through the firmlinks, and listing them would show a near-empty row for half the disk.
- **The scan belongs to the session, not the page**: switching to another sidebar row used to cancel it, and the tool came back to its start screen as if it had forgotten what it was doing. A measurement now keeps running while you browse elsewhere — the sidebar's tool row shows a spinner so it is never invisible — and coming back attaches to the running scan instead of starting a second one. The page's stop button, the toolbar's rescan/stop and starting a different scan remain the only ways to end it.
- **"Show in Finder" no longer starts an application**: revealing an application bundle used to launch the app itself — every row and tile under `/Applications` — and a preference pane opened System Settings, because LaunchServices hands a resource to whatever application claims that kind. A folder is now opened directly only when Finder would open it; anything else is revealed through its enclosing folder. The junk list's reveal had the same shape and is fixed with it.

### Under the hood

- **A tree is walked about 40% faster, and neither cost was the syscall.** Every directory's progress tick went through an actor — 150 k directories meant 150 k suspension/resume pairs for what is two integers — and the enumeration built a `URL` for every entry it returned, including the deep files the measurement only sums, whose path was then rebuilt from that URL as a string. Progress now counts under an unfair lock and entry paths are computed on demand: on `/System/Library` (150,592 directories, 32.8 GB) a scan takes 2.65 s instead of 4.6 s, measured back to back on the same cache, with identical output (32,827,998,208 bytes, same directory count). The readdir counting pass got the same treatment (3.4 s → 2.9 s), and there more workers was tried and does nothing — 6, 10 and 14 all land within 3%.
- **The measurement runs on a fixed pool of workers over one shared queue**, the design the counting pass already used, instead of spawning a task per directory. A task per directory is not bounded by the concurrency limit: a parent task stays alive waiting for its children however deep the tree runs, so the semaphore that capped concurrent *enumerations* capped nothing about how many tasks exist at once. On a real startup disk (1.7 M directories, 252 GB) that peaked at 871 k live tasks and 2.7 GB resident — measured, by counting them — and took 110 s; the same disk now peaks at 483 MB and takes 37 s, with the tree retained exactly as before (219,866 nodes). A deep, leaf-poor tree is the shape that grows a task-per-directory population fastest, and it is now the regression test's fixture.
- **One `getattrlistbulk` call per directory** returns name, node type, allocated size and mount status together, instead of Foundation's `contentsOfDirectory` plus a `resourceValues` round trip per entry; the separate readability probe, child-count pass and first traversal level are merged into the same pass. Mount points are recognized by the kernel's own per-entry flag rather than diffing every path against the mount table, which is both cheaper and immune to firmlink spelling differences. Measured against a Foundation-based traversal on real trees, the sizes are identical while a 112 k-file cache directory measures in 0.45 s instead of 5.3 s and a fresh full-disk scan of a 1.7 M-directory startup disk (252 GB) completes in 37 s.
- **Every string ships in all three languages** — Simplified Chinese, English and Traditional Chinese — including the singular/plural pairs the treemap and the list counts rely on, the tile and hover size/share lines, and the tiles' accessibility labels. Tests pin the placeholder layout of every plural pair the UI renders, because a `.one` form missing its `%lld` crashes the UI the moment it renders.
- **The engine's contracts are pinned by unit tests**, not by the UI: the counting pass must visit exactly the directories the measurement visits, progress events stay throttled well under the directory count, stopping a scan presents nothing, and a deep tree's resident footprint stays bounded. The treemap layout is a pure function, so proportionality, in-bounds tiles, non-overlap and worst-aspect-ratio are all asserted directly, together with the fold threshold and the label rule that have to agree with it.
