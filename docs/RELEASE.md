# Release Notes (Maintainer-Facing)

This document is for Mackit maintainers: signing, notarization, DMG packaging and the Sparkle auto-update pipeline. Regular users should head back to the [README](../README.md).

## One-Command Release (Scripts/build-all.sh)

`Scripts/build-all.sh` drives the whole release end to end: preflight, universal build, Developer ID signing, notarization and stapling (via `build-dmg.sh`), the Sparkle archive and appcast (via `build-update.sh`), and finally `gh release create` with the four assets.

```bash
Scripts/build-all.sh                 # release the version tagged on HEAD
Scripts/build-all.sh --tag 1.2.0     # create and push tag v1.2.0 first
Scripts/build-all.sh --dry-run       # preflight + plan only, builds nothing
```

Credentials come from the environment, or from a gitignored `.env.release` file at the repo root (see `--env-file`). The feed URL, archive URL prefix and notes file default to the conventions below (`releases/latest/download/appcast.xml`, `releases/download/v<tag>/`, `docs/release-notes/v<tag>.md`) and can be overridden. Preflight fails fast on anything that would otherwise surface minutes into notarization: a signing identity that is not a Developer ID Application, incomplete notarization credentials, a missing Sparkle key pair, a release that already exists for the tag, or a dirty working tree. `gh` must be installed and authenticated unless `--skip-release` is passed; `--skip-update` implies `--skip-release` because a release published without its `appcast.xml` breaks the feed for every installed copy. Other options: `--draft`, `--allow-dirty`, `--no-notes` — run `Scripts/build-all.sh --help` for the full list. The stages below remain the reference for recovering a partial release (for example, publishing artifacts manually after a failed `gh release create`).

## Signing and Distribution

`Scripts/build-app.sh` signs locally ad-hoc by default, which is only enough to run on your own machine. To distribute, set the signing identity environment variable and the script switches to Developer ID signing and enables the hardened runtime (a prerequisite for notarization):

```bash
MACKIT_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" Scripts/build-app.sh release
```

The version defaults to the latest git tag (`git describe --tags`) and can be overridden with `MACKIT_VERSION` / `MACKIT_BUILD_NUMBER`. The dSYM is copied next to `Mackit.app` as well, for symbolizing crash reports.

Environment variables supported by `Scripts/build-app.sh`:

| Variable | Purpose |
| --- | --- |
| `MACKIT_SIGN_IDENTITY` | Signing identity. When set, signs as Developer ID and enables the hardened runtime; when unset, signs locally ad-hoc |
| `MACKIT_ARCHES` | Space-separated list of architectures, e.g. `"arm64 x86_64"` for a universal binary; unset builds the native architecture only (the default for development iteration, and the fastest) |
| `MACKIT_VERSION` | Overrides the version (defaults to the latest git tag) |
| `MACKIT_BUILD_NUMBER` | Overrides the build number (defaults to the commit count; Sparkle compares versions via `CFBundleVersion`, which must increase monotonically) |
| `MACKIT_UPDATE_FEED_URL` | Sparkle appcast URL (https). When set, the main app's Info.plist gets `SUFeedURL` and friends, and Sparkle starts with the app; when unset, development builds carry no update source and the update UI is hidden |
| `MACKIT_UPDATE_PUBLIC_KEY` | EdDSA public key (`SUPublicEDKey`), generated by Sparkle's `generate_keys`; used together with the feed |
| `MACKIT_UPDATE_AUTO_CHECK` | Default value of the auto-check toggle, 1 (true) by default |
| `MACKIT_UPDATE_AUTO_UPDATE` | Default value of the auto-download toggle, 0 (false) by default: a found update is offered in the standard alert, which asks before downloading. Enabling it (here or in the app's Settings) makes Sparkle download silently and install on quit without ever prompting — since Sparkle 2.4 that mode shows no prompt at all, so the user is never told a new version exists; the hands-off choice is opt-in |
| `MACKIT_UPDATE_INTERVAL` | Scheduled check interval in seconds, 86400 by default |

## Packaging the DMG

```bash
# Local build (unsigned, runs on this machine only)
Scripts/build-dmg.sh release

# Full deliverable: Developer ID signing + notarization + stapling
MACKIT_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
MACKIT_API_KEY="$HOME/Downloads/AuthKey_XXXXXXXX.p8" \
MACKIT_API_KEY_ID=XXXXXXXX \
MACKIT_API_ISSUER=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx \
Scripts/build-dmg.sh release
```

Artifacts land in `dist/`: `Mackit-<version>.dmg` plus a same-named `.sha256`. The version is read from the built product's Info.plist, i.e. the latest git tag (currently `v1.0.2`).

The DMG contains an Applications shortcut, the install-arrow background image (generated by `Scripts/make-dmg-background.swift`, with coordinates matching the Finder layout) and a volume icon. The first time it runs on a machine, setting the Finder layout pops one "Accessibility / Automation" authorization; the layout only takes effect once allowed. If it is denied or nobody is attending, the script waits `MACKIT_LAYOUT_TIMEOUT` (60 seconds by default) and then skips the layout, which does not affect the DMG itself.

The default build is a universal binary (arm64 + x86_64); signing and notarization both treat the fat file as a whole, with no extra steps. You will see one SDK warning during the build, `x86_64 architecture is deprecated` (from macOS 27 on), which does not affect compilation. Set `MACKIT_ARCHES=arm64` when you only want the Apple silicon slice; the script prints the architectures actually inside the bundle, so you can confirm you are not shipping a half-package.

Notarization credentials, pick one of three:

- App Store Connect API key: `MACKIT_API_KEY` (path to the .p8) + `MACKIT_API_KEY_ID` + `MACKIT_API_ISSUER` (the Issuer ID under App Store Connect › Users and Access › Keys). The key's role must be Admin / App Manager / Developer
- Apple ID: `MACKIT_APPLE_ID` + `MACKIT_APP_PASSWORD` (app-specific password) + `MACKIT_TEAM_ID`
- Keychain profile: first `xcrun notarytool store-credentials "mackit-notary" ...`, then set `MACKIT_NOTARY_PROFILE=mackit-notary`

Notarization hard-requires a Developer ID Application signature: notarytool always rejects packages signed with Apple Development / Apple Distribution identities, and the script errors out directly rather than producing something that looks like a deliverable but cannot pass Gatekeeper. If the certificate is missing from the keychain, create and import it for the right team at developer.apple.com first.

## Auto-Updates (Sparkle 2)

In-app auto-updates run on [Sparkle 2](https://sparkle-project.org): the client periodically fetches the appcast (RSS), compares `CFBundleVersion` to spot a new version, then downloads it, verifies the EdDSA signature and the code signature, replaces the bundle in place and restarts. First installs still use the DMG; the update channel is a separate `.tar.bz2` archive plus `appcast.xml`, both hosted at the same HTTPS location.

The full flow for publishing an update:

```bash
# 1. Generate the signing key pair (once only). The public key is printed; the private key goes into the login keychain.
.build/sparkle-tools/bin/generate_keys

# 2. After tagging, build the deliverable with the update source (feed and public key go into Info.plist)
git tag v1.2.0
MACKIT_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
MACKIT_UPDATE_FEED_URL="https://github.com/virskor/mackit/releases/latest/download/appcast.xml" \
MACKIT_UPDATE_PUBLIC_KEY="<public key printed by generate_keys>" \
Scripts/build-dmg.sh release

# 3. Package the update archive and generate / append the appcast
MACKIT_ED_KEY_FILE=<path to the private key file, never committed to the repo> \
MACKIT_DOWNLOAD_URL_PREFIX="https://github.com/virskor/mackit/releases/download/v1.2.0/" \
MACKIT_NOTES_FILE=notes-1.2.0.md \
Scripts/build-update.sh
```

Step 3 produces `dist/updates/appcast.xml` and `dist/updates/Mackit-<version>.tar.bz2`; upload them to the location `MACKIT_DOWNLOAD_URL_PREFIX` points at. The release notes file (`.html` / `.md` / `.txt`) is embedded in the appcast, so it needs no separate hosting. Keep the historical archives under `MACKIT_UPDATES_DIR` around — future delta updates (binary diffs) will need them.

## Hosting and Publishing (GitHub Releases)

The installer, update archives and appcast are all hosted on GitHub Releases; no server of your own is needed. The feed URL is written into Info.plist at build time via `MACKIT_UPDATE_FEED_URL`, pinned to:

```
https://github.com/virskor/mackit/releases/latest/download/appcast.xml
```

Each Release needs four kinds of assets:

| Asset | Source |
| --- | --- |
| `Mackit-<version>.dmg` | `build-dmg.sh` output (signed, notarized, stapled) |
| `Mackit-<version>.dmg.sha256` | Same as above, generated alongside the DMG |
| `Mackit-<version>.tar.bz2` | `build-update.sh` output |
| `appcast.xml` | Same as above; `MACKIT_DOWNLOAD_URL_PREFIX` must point at **that release's own tag** |

`releases/latest` always resolves to the newest full release (drafts and prereleases are skipped), so:

- every release must carry the `appcast.xml` generated for it; otherwise the version `latest` resolves to has no feed, and older copies checking for updates get a 404
- never mark a full release as a prerelease — a version skipped by `latest` effectively disappears from the feed
- `MACKIT_DOWNLOAD_URL_PREFIX` is per-tag (`.../releases/download/v1.2.0/`), so archive URLs are fixed the moment they are published and never drift

Publishing with the GitHub CLI:

```bash
gh release create v1.2.0 \
  dist/Mackit-1.2.0.dmg dist/Mackit-1.2.0.dmg.sha256 \
  dist/updates/Mackit-1.2.0.tar.bz2 dist/updates/appcast.xml \
  --title "Mackit 1.2.0" --notes-file docs/release-notes/v1.2.0.md
```

While the repo is still private, anonymous fetches of the feed and assets return 404 (GitHub requires authentication for private-repo assets); that is expected. Once the repo is public, anonymous downloads work and the update pipeline comes alive. The `gh-pages` branch also holds a cumulative appcast (with entries for every historical version), for switching `MACKIT_UPDATE_FEED_URL` to a shorter feed address later if GitHub Pages is enabled; both pipelines produce identical output and can be swapped at any time.

A few easy-to-trip points:

- **The build number must increase monotonically.** Sparkle compares versions by `CFBundleVersion`; `build-app.sh` defaults to the commit count (`git rev-list --count HEAD`), which grows with every commit naturally. Override it with `MACKIT_BUILD_NUMBER` in CI. Hard-coding one value makes the updater believe forever that "what is installed is the latest"
- **The update package and its host must be signed by the same Developer ID identity** — Sparkle's XPC service checks that the Team IDs match on both ends. The host app is notarized, and the update package is downloaded and written to disk by the app itself (not through the browser's quarantine), so the update package itself is not required to be notarized
- **The archive format is fixed at `.tar.bz2`**: Sparkle only accepts zip / tar / tar.gz / tar.bz2 / tar.xz / .aar at runtime — there is no `.tar.zst`; pick the wrong format and you get "download succeeded but unpacking failed"
- **The private key never enters the repo.** The file `MACKIT_ED_KEY_FILE` points at is equivalent to the private key in the login keychain; leaking it lets someone push malicious updates. Put it in a CI secret, or in the keychain on a real machine
- Running straight from the DMG (without dragging into `/Applications`) makes Sparkle refuse updates; that is expected
- Development builds do not set `MACKIT_UPDATE_FEED_URL`, so Info.plist carries no Sparkle keys, the updater never starts, and the "Updates" section of the settings page is hidden as well

Verifying the update pipeline locally: start a local HTTP server pointing at the updates directory and have an older build check it. Either of two approaches:

1. When building the older version, set `MACKIT_UPDATE_FEED_URL` straight to `http://127.0.0.1:8765/appcast.xml` and `MACKIT_DOWNLOAD_URL_PREFIX` to `http://127.0.0.1:8765/`, so both the appcast and the archives point locally;
2. Without rebuilding, point the installed older copy at it: `defaults write cn.mingcui.mackit SUFeedURL http://127.0.0.1:8765/appcast.xml` — Sparkle's user-defaults override takes precedence over Info.plist; after testing, `defaults delete cn.mingcui.mackit SUFeedURL` restores the production address.

An HTTP (non-HTTPS) feed is not blocked: Sparkle then insists that the update carry an EdDSA signature and that the host be signed (both hold here), and the archive enclosure's scheme allows http as well. Launch the older build and you see the whole "new version found → download → install and restart" flow.

The settings page's "Updates" section offers two toggles: auto-check (on by default, once every 24 hours) and auto-download (downloads in the background once a new version is found, still asking before installing). "Check Now…" sits below the Settings item in the App menu. All update-related logs go through the `updates` category of `os.Logger`.

## Credential Security

- Private key material such as `.p8` / `.p12` / `.pem` / `.key` never enters the repo; `.gitignore` already blocks them, and the pre-commit hook (`Scripts/install-git-hooks.sh`) scans the staging area as a backstop
- Public certificates are public information and may be archived in the repo; the private keys matching them may not
- In CI, credentials go in secrets; on a real machine, in the login keychain (`generate_keys` can store them directly)
